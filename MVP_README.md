# PersonalCloud

**PersonalCloud is a local-first, peer-to-peer file access MVP.** Each running node owns its files, exposes a small authenticated node API, and can request files that another paired node has explicitly shared with it. Files are not uploaded to a central storage service.

> This is a working desktop/Linux MVP, not a production-ready public-internet cloud. Read the security and scope notes below before exposing a node to another network.

## What is implemented

- A browser dashboard served by the Java process (plain HTML, CSS, and JavaScript).
- Recursive indexing of regular files under a configured storage root.
- A one-time pairing code, valid for 10 minutes and consumed after use.
- Per-peer bearer tokens. The owner stores only a SHA-256 hash for incoming tokens.
- Per-file `VIEW` and `MODIFY` grants to an incoming paired device.
- Direct node-to-node HTTP requests for remote share listing and file streaming.
- `VIEW`: remote peer can list and download the shared original.
- `MODIFY`: also allows the remote peer to delete the original on its owner device.
- File path containment checks; absolute paths, traversal outside the root, and symbolic links are rejected.
- Atomic, local properties-file persistence; no third-party Java dependencies.

## Requirements

- JDK 21 or newer. JDK 26 is fine.
- Linux, macOS, or Windows with a shell capable of running the scripts. The scripts here are written for Bash.
- A browser.

The server uses the JDK's built-in `HttpServer` and `HttpClient`, with virtual threads for request handling. No Maven, Gradle, database server, Node.js, or frontend build is required.

## Run your first node

```bash
chmod +x build.sh run.sh
./build.sh
./run.sh
```

Open `http://localhost:8787` in your browser. On first startup, the terminal prints:

- Username: `admin`
- A generated password
- The path to `data/admin-password.txt`

The browser asks for HTTP Basic authentication. Keep that password private. It is generated once and reused on subsequent starts. The `data/` directory contains the node identity and local peer/share state; do not share it.

Default locations:

- Data/state: `./data/`
- Files indexed by this node: `~/PersonalCloud/storage/`

Copy a test file into the storage directory and press **Refresh index**.

## Test with two nodes on one computer

This is useful before pairing two physical devices. Open two terminals in the project directory.

**Terminal A — node A**

```bash
PERSONALCLOUD_NAME="Laptop-A" \
PERSONALCLOUD_PORT=8787 \
PERSONALCLOUD_DATA_DIR="$PWD/data-a" \
PERSONALCLOUD_STORAGE_ROOT="$PWD/storage-a" \
./run.sh
```

**Terminal B — node B**

```bash
PERSONALCLOUD_NAME="Laptop-B" \
PERSONALCLOUD_PORT=8788 \
PERSONALCLOUD_DATA_DIR="$PWD/data-b" \
PERSONALCLOUD_STORAGE_ROOT="$PWD/storage-b" \
./run.sh
```

Each node has a separate identity, password, state file, and storage root. Put a test file in `storage-a/` and then:

1. Open `http://localhost:8787`. Generate a one-time pairing code on node A.
2. Open `http://localhost:8788`. Enter `http://localhost:8787` and the code under **Pair a device**.
3. On node A, refresh the device list. Node B should appear as an **Incoming** paired device.
4. On node A, grant node B `VIEW` access to the relative path of your test file, e.g. `sample.txt`.
5. On node B, choose Laptop-A under **Remote files** and click **Load remote shares**.
6. Download the file. It is streamed from node A; no central storage is involved.

To test deletion, create a separate throwaway test file and grant `MODIFY`. Deleting it from node B deletes the original on node A. Do not test this with important files.

## Use with two physical computers on the same LAN

1. Start both nodes with `PERSONALCLOUD_BIND_ADDRESS=0.0.0.0 ./run.sh` so the peer API is reachable on the LAN. The default is loopback-only (`127.0.0.1`) for safety.
2. On the receiving device's dashboard, enter the source node's reachable LAN URL, for example `http://192.168.1.20:8787`, and the one-time code generated by that source node.
3. Allow the configured port through the source device's firewall only on the trusted LAN.
4. Grant individual files from the source node dashboard.

The browser dashboard can stay local to each device (`http://localhost:PORT`). The Java node APIs communicate directly between device processes.

## Configuration

All configuration is optional and supplied through environment variables:

| Variable | Default | Purpose |
|---|---|---|
| `PERSONALCLOUD_NAME` | machine hostname | Friendly device name |
| `PERSONALCLOUD_PORT` | `8787` | HTTP port |
| `PERSONALCLOUD_BIND_ADDRESS` | `127.0.0.1` | Listener address; set to `0.0.0.0` only when you intentionally need LAN access |
| `PERSONALCLOUD_DATA_DIR` | `./data` | Node identity, password, peer and grant state |
| `PERSONALCLOUD_STORAGE_ROOT` | `~/PersonalCloud/storage` | Directory this node is allowed to index and share |

Use a different `PERSONALCLOUD_DATA_DIR` and `PERSONALCLOUD_STORAGE_ROOT` for each separate node instance on the same computer.

## Architecture

```text
Browser dashboard (same device)
          |
          | local management API (HTTP Basic)
          v
   PersonalCloud node B  <====== authenticated direct HTTP ======>  PersonalCloud node A
   - local index                                                       - local index
   - peer registry                                                     - peer trust records
   - outgoing peer token                                               - per-file grants
   - remote-share view                                                 - original file stays here
          |                                                                        |
          +------------------------- file stream ---------------------------------+
```

Each instance can act as both a requester and a file-serving node. Pairing is directional: when B enters A's code, A trusts B and B receives a token to request A's shares. To allow A to request files from B too, repeat pairing in the opposite direction (B generates a code; A enters B's URL and code).

## Important limitations — do not mistake this for production security

- **No HTTPS is built in.** HTTP Basic credentials, pairing codes, and peer bearer tokens are not protected in transit on an untrusted network. Use this MVP only on a trusted LAN or inside a properly configured VPN such as WireGuard/Tailscale. Do not port-forward it to the public internet.
- **No NAT traversal or relay.** Peers must have a mutually reachable address (same LAN, VPN, or a deliberately configured route). The app does not discover peers across the internet automatically.
- **No Android agent in this ZIP.** This build runs on desktop/server operating systems with a JDK. Android needs a separate app/service implementation and background-execution/storage integration.
- **No background synchronization.** This is file access and transfer, not a sync engine.
- **Metadata persistence uses a local `Properties` file, not SQLite.** This keeps the initial MVP dependency-free. A database migration is appropriate before larger-scale multi-user use.
- **No multi-user accounts, audit log, rate limiting, resumable transfer, or conflict handling.**
- **The web admin password is stored locally** in `data/admin-password.txt` to support unattended restarts. Protect the data directory and machine account.

## Suggested next hardening milestones

1. Add TLS or require a VPN interface and reject unsafe non-VPN peers.
2. Add rate limiting, audit records, token rotation, and explicit peer revocation UX.
3. Migrate state persistence to SQLite with schema migrations.
4. Add resumable/chunked integrity-checked transfers and file-change monitoring.
5. Implement the Android node as a separate client/agent.
6. Add authenticated device discovery and an optional rendezvous service (coordination only, no file storage) for devices behind NAT.

## Data and privacy

The storage root is the only area that this node's file indexer and share service can access. Shared file contents are read from that root when requested; they are not copied to a central store. Remote deletion is deliberately available only when the owner granted `MODIFY`.

## Current implementation stack

- Java 17+ standard library (`HttpServer`, `HttpClient`, NIO, concurrency, crypto APIs)
- HTML, CSS, and vanilla JavaScript for the browser dashboard
- `Properties`-backed local persistence for this MVP
- No external service or frontend package manager

The earlier design direction included Spring Boot and SQLite. This first runnable node intentionally uses the JDK HTTP server and a small local state file so the project can be built and run with the JDK alone. The service boundaries are separated so the persistence layer can be replaced with SQLite and the HTTP server can later move to Spring Boot without changing the peer/file permission model.
